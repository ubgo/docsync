# docsync — repo rules

## Start here

A new session reads this section first; it is the map. The rules below it are the detail.

**What docsync is.** A Go CLI (`ds`) and library that binds documentation sentences to the code, config and facts they describe, and fails a check when the thing behind a sentence changes. Public at `github.com/ubgo/docsync`, Apache-2.0.

**Where everything lives.**

| Need | Read |
|---|---|
| What the tool does, for a user | `docs/guide/README.md` (13 pages: how it works, getting started, directives, languages, every command and config key, CI, agents, integrations, library, cross-repo, secrets and runs, troubleshooting) |
| The normative design | `docs/SPEC.md`; section 38 lists what is specified but not built |
| How it is tested, and why each check exists | `CONTRIBUTING.md`, "How docsync is tested" (table of every gate) and "Writing guide pages" (the guide is executable) |
| What changed, release by release | `CHANGELOG.md` |
| Every fixed bug, by docsync's own number | `testdata/fixed-bugs.txt` (bug numbers, never GitHub `#N`) |
| Every absolute sentence in the spec and README, and the test that pins it | `testdata/promises.txt` |
| A real user's report and its regression cases | `docs/FIELD-FINDINGS-*.md`, `scripts/e2e/field-findings.sh` |
| Build, test, release commands | `Taskfile.yml` (`task --list`); releasing is the README's "Releasing" section |
| Private history (pre-public git bundle, old issues, internal repo names) | `docsi/` (gitignored symlink to the private repo; never published) |

**Current state (2026-10-04).** Latest releases: `ds/v0.1.6` and `cli/v0.1.6`, library `v0.1.4`, `ext/structured/v0.1.1`, `ext/treesitter/v0.1.2`, `ext/records/sqlite/v0.1.1`. Every bug found so far is fixed and released: 115 entries in `testdata/fixed-bugs.txt`, numbered 1 to 135 with gaps where a fix area left its reserved range unused, so the next bug is 136. 0.1.5 fixed 81 of them, found by writing the guide by running every behaviour as a user would; 0.1.6 made the VS Code extension work in a real editor (130, 131; `task vscode:try` opens a demo) and let remote defs bind whole blocks (132–135, GitHub issue 3: `pick=yaml:<mapping>`, `pick=toml:<table>`, `pick=symbol:<name>`; YAML picks share `internal/keypath` with the config tier). `~/.local/bin/ds` is a symlink to `bin/ds` and other sessions run it live: build experiments to a temporary directory, never into `bin/ds`. GitHub issues: none open. Remaining work is the unbuilt list in SPEC section 38, and whatever real use turns up next.

**How to work here.**

1. Run `task` before saying anything is done; it is the whole gate (see Workflow). `task docs:test PAGE=../docs/guide/<page>.md` runs one guide page.
2. A bug becomes a test first: reproduce it with `bin/ds`, write the unit test and, if it spans commands, an e2e case; see the test fail on the unfixed code; then fix. Add it to `testdata/fixed-bugs.txt` with the next number and reference it as `bug N` in the test.
3. A user-visible change updates the guide page that shows it (the page is a test and will fail otherwise), the spec, and `CHANGELOG.md` under `[Unreleased]`.
4. Anything that changes an extractor, a grammar table or what a hash covers: run `task extract:diff` and say what it reports. A changed hash re-flags every acked citation in every repository using docsync.
5. Windows and Linux are checked by `.github/workflows/windows.yml`, manual only: `gh workflow run windows.yml`, then read the result once with `gh run view`. Run it before a release.
6. Never commit, push, tag or release without the owner's go-ahead for that change. Releases go through volt in dependency order (README, Releasing), each module's `go.mod` re-pinned with `GOWORK=off go mod tidy` once its dependencies are tagged; then fix the release page titles and notes (volt's defaults are thin).
7. Never mention Claude, AI or Anthropic in commits, PRs, issues, release notes or docs, and never hard-wrap markdown.

Read `docs/SPEC.md` before changing behaviour; it is normative and every rule has a fixture under `testdata/conformance`. If the spec and the fixtures disagree, the fixtures win and the spec gets fixed in the same change.

## Invariants

- The root module `github.com/ubgo/docsync` imports the standard library only. No exceptions, ever. Anything that needs a dependency lives in a sub-module (`cli/`, `ext/...`) with its own `go.mod`.
- The library never writes a file, reads the environment or `$HOME`, or opens the network. Operations that would write return an `Edit`; the CLI applies it. Hooks for git, providers, and URLs come in through functional options.
- Every package holds 100% statement coverage. `task` runs `scripts/coverage-gate.sh` and fails below that. Reach coverage by testing the behaviour, never by deleting the branch to dodge it, and never by excluding files.
- Closed sets are named constants with a `*Values` list beside them. No bare state, verb, key, or severity strings at use sites.
- One finding state per rule, one fixture per state. Adding a state means adding it to `check.StateValues`, the severity table, a remedy, and a conformance fixture; `TestConformanceStatesCovered` enforces the last part.

## Dogfooding

The repo tracks its own docs under `prefix = "dsself"` — the default `ds` prefix cannot be used, because the source and fixtures are full of `ds:` directives written as examples and the scanner would read them as real. `task dogfood` runs `./bin/ds check --full` and is part of `task`. It checks and never scans: `ds scan` rewrites the ledger header's `scanned_at`, and a gate that dirties committed state on every run is a gate everyone learns to ignore.

A bound block that changes makes `task` fail. Fix it the way a user would — edit the sentence in `README.md` or `docs/SPEC.md` if it is now wrong, then `./bin/ds scan` and `./bin/ds ack <id> --doc <doc> --line <n> --note '…'`. Never ack without reading the sentence, and never delete the binding to make the gate quiet.

Bindings are deliberately few: only where a doc sentence restates a value that lives in the code. Add one with `./bin/ds def <file>#<symbol> --owner @docsync --stability stable`, then `<!-- dsself:block id=… -->` on its own line above the sentence. Choose the stability from what you want to be told about; `api` does not flag a body-only change, which is wrong for a list whose contents are the contract.

## Workflow

- `task` is the gate: gofumpt check, vet, staticcheck, race tests, coverage gate, `js`, `dogfood`, `corpus`, `extract:diff` against `HEAD`, `e2e`, `docs:test` and `xbuild`. Run it before saying anything is done. `CONTRIBUTING.md` has the table of every check and the class of bug each one catches.
- `task e2e` drives the built binary through `scripts/e2e/*.sh`: several commands in sequence, git history, merges, more than one repo — the things unit tests cannot reach, and where every one of the first twelve bugs lived. A behaviour that spans commands gets a case there. Each matrix prints `---- N passed, M failed ----`; `run.sh` fails on a failed case, a missing tally, or a shell error (`command not found`, `line N:`), because a check that never ran must not count as passing. `integrations.sh` runs the Docusaurus plugin and remark transformer and a real Hugo build against the built binary, because their own tests use a fake `ds` and a fake accepts any flag or field; it prints `SKIP` when `node` or `hugo` is absent.
- `task corpus` runs the built binary over the last commit of real third-party repositories (never their working tree, which is someone's half-finished work) in every language with a syntax tier (default, where present on this machine: `ubgo/auth` and `99designs/gqlgen` in Go, `Aider-AI/aider` in Python, `vercel/ai-chatbot` and `stackblitz/bolt.new` in TypeScript and TSX; add more with `CORPUS=/path/a:/path/b`) and asserts **invariants only** — every def starts on the first code line below its directive, no two ids share a block, no block closes more brackets than it opens (the language-neutral form of "an entry's extent swallowed its holder's closing paren or brace"), every recorded id locates back to its own range, a second scan of unchanged source gives the same ledger. There are no expected values, so nothing in it encodes what the author thought the corpus contained, and the checks are computed from the files and the ledger rather than read off the tool's own findings — an invariant that reads a finding only confirms the tool agrees with itself. It prints SKIP and succeeds when no corpus is present. Why it exists: every other gate here tests docsync against code shaped like the code in this repository, which is how a constant inside `const ( … )` went unhandled through 245 e2e cases, fuzzing, dogfooding and five modules at 100% statements until a consumer reported it (bug 18). 18 such groups exist across all of this repo's fixtures; 211 in the one repository that found the bug.

- `testdata/fixed-bugs.txt` lists every fixed bug by docsync's own bug number, and `TestEveryFixedBugIsPinned` fails for any that no test or e2e script references in the form `bug N`, `(bug N)` or `bugs N, M and K`. When a bug is fixed, add it there in the same change as the test that proves it. Put the reference on the test that actually exercises the fix -- the gate checks the link exists, not that it is honest. The numbers are not GitHub issue numbers: the original reports, and the git history before the public baseline, are archived in `docsi/` (private, never pushed), and a `#N` would link to whatever issue N of the public repository is.
- `testdata/promises.txt` lists every absolute sentence in `docs/SPEC.md` and `README.md` (never, always, refuses, must not, deterministic, hard error), and `TestSpecPromisesArePinned` fails when one is unlisted, when a listed quote no longer appears verbatim, or when a `test` promise has no `*_test.go` or `scripts/**/*.sh` naming it as `promise:<id>`. Writing a promise into the spec means listing it and writing the test that proves it, in the same change; `prose: <reason>` is for sentences that are not tool behaviour (advice to authors, non-goals, examples), never a way to skip a test. Tag only a test that actually asserts the promise -- the gate checks that the link exists, not that it is honest. This gate exists because a sweep of the spec's promises against the built binary found five that did not hold and that no test checked.
- `scripts/e2e/secrets.sh` runs every command that prints block content, and the MCP tools, over a repository citing a secret in three states, and fails if the value appears anywhere. A new command that prints content is a new place to leak: add it to that list.
- `scripts/e2e/field-findings.sh` holds one case per finding in a field report (`docs/FIELD-FINDINGS-*.md`). A finding a real user hit becomes a case there, pinned against the built binary, and the matrix is checked to FAIL on the build before the fix -- a regression test that passes on the broken build is not one.
- `task extract:diff` (`REF=<git ref>`, default `HEAD~1`; `task` runs it against `HEAD`, so every uncommitted change is compared with the last commit) builds that ref and the working tree, anchors a corpus copy with directives inserted by awk rather than by `ds` so neither build influences what the other is asked to extract, scans byte-identical copies with both, and compares every block by id. **Run it before any change to an extractor, a grammar table, or a hashing rule.** The danger in that code is not a new bug but a changed hash: a block that still binds, names the same thing, and covers the same lines, yet hashes differently, makes every acked citation of it report drift in every repository that had it — a repo-wide false alarm that no unit test can see, because each test asserts what the current build does and nothing compares builds. It fails only on that case, and reports repairs (symbol or extent moved) and newly bindable blocks separately, since comparing against a pre-fix baseline must show differences. Two traps it has already sprung: an id generator that produced duplicates turned a `join` into a million phantom changes, so it now refuses to compare ledgers whose ids repeat; and judging "was correct before" by the start line alone called 23 repairs regressions, because the old build had bound an interface method's first parameter, which begins on the same line as the method. Symbol and extent together are the test.

- `task docs:test` (part of `task`) runs every example in `docs/guide/` against the built binary through `cli/internal/doctest`: a `file=` block is written, a `$ ` session is run and its output compared, `<!-- doctest -->` holds hidden setup, `<!-- doctest:skip REASON -->` skips a block with a counted reason. Ids are paired between the page and the real run, so a page can mint with `ds def` and then use the id it showed. Why it exists: the guide's writers, running every documented behaviour as a user would, found some eighty disagreements between the binary and its docs that 400 e2e cases and 100% coverage had not, because every other test shares its author's expectations. A behaviour change that breaks a guide example fails the gate; fix the page or the binary, never elide the disagreement with `…`.
- `cli/cmd/ds/hashprop_test.go` changes every code character of a def, one at a time, in every tier the binary ships, and requires the block to stop looking the same. Bug 22 (Go string text outside the hash) is the case it exists for: every earlier hashing test changed a number.
- `task fuzz:all` (`FUZZTIME=30s` each) searches every fuzz target; a failing input lands in the package's `testdata/fuzz/` and plain `go test` replays it from then on, so commit it with the fix. Fuzz properties state what must hold for every input (round trips, idempotence, bounds) rather than expected values, so they cannot share an assumption with the code.
- `task perf` times the built binary against the SPEC §33 targets (full scan under 60s, incremental check under 2s, `impact --staged` under 1s) on a generated git repo of `FILES` files, default 100000, and fails on a miss. It is not part of `task` because building and committing that tree takes minutes; run it before a release and after any change to scanning, the extraction cache, or ledger loading.
- A test is only evidence once it has been seen to fail: break the code it guards, watch it fail, restore from a backup (never `git checkout`). Several tests here passed vacuously until that was done.
- `task conformance:update` regenerates `expected.json` files and the JSON goldens. Read the resulting diff line by line; a changed expectation is a changed rule and needs a reason in the commit message.
- The JSON goldens under `testdata/golden` pin the `json_format = 1` contract. Changes must be additive; a removed or renamed field needs a format bump.
- Conformance fixtures are `before/` and `after/` trees plus optional `config.toml` and `acks.json`. Dates are evaluated at 2026-09-06 (`conformanceNow`), so claims and sunsets in fixtures are written against that day.
- The shell aliases `rm` to an interactive prompt; use `/bin/rm -rf` in scripts and Taskfile commands.
- gopls reports "not in workspace" for every file because there is no `go.work`; the compiler is the authority.

## Layout

`directive id block extract pick sentence scan ledger match check render config procplugin workspace records` are the packages; `docsync.go`, `define.go`, `agent.go` are the root API; `internal/{glob,textnorm,difflib,duration,linerange}` are shared helpers, one grammar each so no two packages parse the same thing differently. `cli/` is its own module (cobra) with `cmd/ds`; `task cli` gates it; `task cli:build` produces `bin/ds` and the `bin/ds-resolve-*` plugins, and `task install` symlinks all of them into `$HOME/.local/bin` (override with `DEST=`) so the development build is what runs while testing, with no reinstall after a rebuild. `ext/structured/` (yaml.v3, go-toml, hcl/v2) is gated by `task ext`; `ext/treesitter/` (smacker/go-tree-sitter, cgo, needs a C compiler) by `task ext:treesitter`; `ext/records/sqlite/` (modernc.org/sqlite) by `task ext:sqlite`; the JavaScript integrations `integrations/docusaurus/` and `editors/vscode/` by `task js` (node --test with 100% line, branch, and function thresholds). `cmd/ds` imports the structured and tree-sitter modules, so the standard binary carries every shipped tier; `integrations/github` (composite Action + workflow templates) and `integrations/hugo` (Hugo module reading `ds export hugo` data) are files, not Go, and the pre-commit hooks are `.pre-commit-hooks.yaml` at the repository root, the only place pre-commit reads them. The root `go.work` joins every module for development; each `go.mod` requires the others at published versions and carries no `replace`, because `go install …@version` refuses a module with one. Releases go through volt in dependency order (README, Releasing): root, then the `ext` modules, then `cli` and the `ds` binary, re-pinning each `go.mod` with `GOWORK=off go mod tidy` once its dependencies are tagged. `install.sh` / `install.ps1` are generated by `volt gen install cli/cmd/ds` and never edited by hand. `go mod tidy` in ext modules may need `-e` offline when a dependency's own test dependency is not cached. The cli cannot import `internal/` packages of the root; anything it needs is exported (for example `scan.CountMatches`). Build order and what is still missing are in `docs/SPEC.md` section 38 and the README status section.
